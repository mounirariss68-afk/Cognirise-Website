AI guardrails framework / any sector

Set, Prove & Hold

The usual pattern: write down what the AI must never do, put the rule in the AI's instructions, and call it a guardrail. This is about the difference between a rule the AI has been asked to follow and one it cannot break.

A guardrail is only as strong as the layer it is actually built into.

Set, Prove & Hold (4 + 4 + 4)

Three things happen to every guardrail. Four steps in each.

Set(4)
Steps · before you build
  1. Name what must never happen
  2. Build it into the strongest layer you can
  3. Choose what happens when it triggers
  4. Give each rule an owner
Prove(4)
Tests · before you launch
  1. Attack each rule directly
  2. Widen the attack to the whole system
  3. Count what it blocks wrongly
  4. Record the result, with a date
Hold(4)
Disciplines · every day after
  1. Watch the blocked attempts
  2. Re-test on every change
  3. Add new rules, retire old ones
  4. Report strength, not count

Where the rule is enforced decides everything else

The first decision inside Set is which of four places the rule lives in. The same rule can be written in any of them, and the choice decides whether someone determined can get past it.

One rule, written four different ways “Never reveal another customer's data.”
Layer What it is In this example What gets past it Strength
1 · Policy A rule in a document A line in the AI usage policy. The system never sees it. Anyone who has not read it ●○○○
2 · Prompt A line in the AI's instructions The AI is told not to. The other customer's data is still in front of it. One well-crafted instruction, typed or hidden in a document ●●○○
3 · Runtime Software outside the AI that checks what goes in and out Any answer containing another customer's record is blocked before it leaves. Gaps in what the scanner recognises — an odd format, another language ●●●○
4 · Architecture The AI is given only the data and tools the task needs The search returns only the signed-in customer's own records. Nothing — the data was never sent ●●●●

Layer 4 is not about withholding. The AI still gets everything it needs to do the job — it just never gets more than that.

Build every rule into the strongest layer that can carry it. Layers 1 and 2 ask the AI to behave. Layers 3 and 4 do not ask. Stop at layer 2 and your guardrails are requests, not controls.

The layer decides how you build it, test it and re-test it

This grid is the framework. Layers down the side, the three stages across the top.

Layer Set — how you build it Prove — how you test it Hold — when you re-test
1 · Policy Write it in a document Nothing to test Never — it is not connected to anything
2 · Prompt Put it in the AI's instructions Attack it. Expect it to fail some of the time. Every model or instruction change — so, constantly
3 · Runtime Add a check outside the AI, on the way in or out Attack it, and count what it blocks wrongly When the scanner, the model or the languages change
4 · Architecture Give the AI only the data and tools the task needs Check the scoping is actually in place Only when the architecture changes — rarely

Read the bottom row against the second. A rule in the AI's instructions is quick to write and then needs re-testing every time anything moves. The same rule built into the architecture is real work once, and then holds by itself. Layer choice is a maintenance decision as much as a security one.

One number is worth tracking above the rest: how many of your guardrails sit at each layer. Set assigns it, Prove tells you whether the claimed layer is real, Hold reports it over time.

What this is built from

Nothing invented here. The ethics frameworks tell you what to forbid. The security ones tell you how it gets bypassed. A policy built on the first alone will name the right rules and miss every way around them.

Where to start

Three moves, in this order. The first takes an afternoon.

Move 1

List every guardrail you think you have, and mark which layer each one lives at. Then count how many sit at layers 3 and 4. That number is the finding.

Move 2

Take the three that matter most and try to break them. Two people, one afternoon. Whatever survives is worth keeping; whatever does not was never a control.

Move 3

Move one guardrail to a stronger layer. Start with the least technical option: narrow what the AI is given to what the task actually needs.

Set — deciding what must never happen (4)

A guardrail is a rule you can test. "Be helpful and safe" cannot be tested. "Never tell an applicant whether they qualify" can — you can try to make it happen and see what the system does.

4 steps · sequential
Step 1Name
Step 2Build
Step 3Choose
Step 4Assign
1

Name what must never happen

A rule you could try to break this afternoon.

  • Write a “never”, not a value — “be safe” cannot be tested
  • Write it for this system — not copied from a vendor's generic list
  • Three sources — the law, the damage this system could do, the known ways AI breaks
OwnerRisk and legal, with the product owner
OutputA numbered rule list, versioned
Fails when The list is copied from a vendor's responsible-AI page, so it names risks this system does not have and misses the ones it does.
2

Build it into the strongest layer you can

Start at layer 4. Ask what the task needs before you ask what to forbid.

  • Layer 4 — give the AI only the data and tools this task needs
  • Layer 3 — if not, add a check outside the AI on the way in or out
  • Layer 2 — only then the AI's instructions, marked as bypassable
OwnerEngineering, challenged by security
OutputEvery rule labelled with its layer
WatchHow many sit at 3–4 versus 1–2
Fails when Every rule goes into the AI's instructions because that is fastest, until they are so long the AI follows them inconsistently.
3

Choose what happens when it triggers

There are four options. Pick one per rule — and if you block, say why.

  • Four responses — block, redact, escalate to a human, or allow and log
  • Match the response to the rule, rather than one setting for everything
  • Tell the user what to do instead — a refused user does not stop needing the thing
OwnerProduct owner, with risk
OutputA response type and user wording per rule
Fails when Everything is set to block, so the business quietly builds a path around the system.
4

Give each rule an owner

Someone who can say it is still needed, and who answers when it fails.

  • A named role, not a committee
  • Authority to retire it — otherwise the list only grows until it is too long to test
  • A review date, because rules go out of date as the system changes
OwnerAI governance
OutputThe guardrail register: rule · layer · response · owner
Fails when Ownership sits with a central team that did not write the rule and cannot judge whether it still applies.

Set produces one list. Every line reads rule · layer · what happens · who owns it. A guardrail that is not on the list does not exist — and if the layer column is mostly 1s and 2s, the list is longer than the protection.

Prove — showing it actually holds (4)

Every step here produces evidence with a date on it. "We have a guardrail" is a claim. "It stopped 47 of 50 attempts on 12 September" is a control.

4 tests · all four, before launch
Test 1Attack
Test 2Red-team
Test 3Count
Test 4Record
1

Attack each rule directly

Test against the exact thing the rule exists to stop.

  • One test set per rule, written from the rule itself
  • Try it plainly, then sideways — role-play, translation, or hidden inside a document
  • Test in every language you serve — the checking software is weakest outside English
SourceOWASP GenAI LLM Top 10
OutputPass rate per rule, per language
Fails when The tests are the same examples the guardrail was tuned on, so they measure what it memorised.
2

Widen the attack to the whole system

Attacks arrive through the documents, the tools and the output path — not only through the chat box.

  • Documents it reads — text can contain instructions, and the AI may follow them
  • Tools it can use — what it can set off, and whose permissions it borrows
  • Where the answer goes — shown on a page, run as code, written into another system
SourceMITRE ATLAS
Run bySecurity, or a specialist for high-impact systems
Fails when The red team is given the model API instead of the deployed product, so it tests the one part the vendor already hardened.
3

Count what it blocks wrongly

If it gets in the way of real work, someone will turn it off — and that decision will not be written down anywhere.

  • Run real traffic through it before launch, not just attack cases
  • Agree a limit on how often it may block legitimate work, and treat going over it as a bug
  • Tune it or move it to a stronger layer — never relax it
OwnerProduct owner, with the business users
OutputHow often it blocked legitimate work, against the agreed limit
Fails when Only attack blocks are reported, so guardrails look free and the ones quietly disabled later never appear anywhere.
4

Record the result with a date on it

“We have a guardrail” is a claim. “It stopped 47 of 50 attempts on 12 September” is a control.

  • What was tested, against which rule, in which languages
  • Which versions — model, instructions, tools, documents
  • The date — the evidence expires the moment any of those versions changes
Held inThe guardrail register
SourceISO/IEC 42001, which asks for proof that controls ran
Fails when The evidence names the product but not the AI model version, so nobody can tell whether it still applies.

Four questions for any team that says its guardrails are in place: what is the pass rate, against which attempts, on which version, and when was it measured? If they cannot answer all four, the guardrails have not been tested.

Hold — keeping them holding (4)

Guardrails decay. The model changes, the prompt changes, the tools change, the attackers get better, and the prohibition list goes stale in both directions. These four run for as long as the system does.

4 disciplines · concurrent
Discipline 1Watch
Discipline 2Re-test
Discipline 3Revisit
Discipline 4Report
1

Watch the blocked attempts

Every block tells you what somebody wanted the system to do.

  • Log enough context to see what was being attempted, not just that it fired
  • Alert on spikes and on new techniques — one method you have not seen before is worth more than a hundred repeats of one you have
  • Separate attackers from confused users — most triggers are the second, which is a design problem
OwnerSecurity operations
CadenceContinuous, reviewed monthly
Fails when Triggers get counted but never read, so you know how often guardrails fired and nothing about what for.
2

Re-test on every change

A guardrail proven against last quarter's model is not proven.

  • Five things move — the model, the instructions, the tools, the documents, the guardrail itself
  • Automate the tests so re-running them costs nothing; a check that takes a week gets skipped
  • A drop in pass rate blocks the release
OwnerEngineering, checked automatically before each release
CadencePer release, and on vendor notice
Fails when The vendor updates the hosted model with no notification clause in the contract, so the first sign is a live failure.
3

Add new rules, retire old ones

New capabilities create new risks. Old rules outlive their reason.

  • Every new tool or data source needs its own rule
  • Retire what no longer applies, with the owner's sign-off and a note of why
  • Move rules to stronger layers when you can — anything still sitting in the instructions is a candidate
OwnerThe rule's named owner
CadenceOn change, and on a fixed review date
Fails when The list only ever grows, so it becomes too long to test and testing narrows to the few everyone remembers.
4

Report how strong they are, not how many

“Forty-one guardrails” is a press release. “Six enforced by anything other than asking the AI” is a finding.

  • How many sit at each layer — the one number that shows real progress
  • Pass rates, with the version they were measured on
  • Wrong blocks against that agreed limit, so the cost sits next to the benefit
OwnerAI governance
CadenceMonthly to committee, quarterly to board
Fails when The report counts guardrails but not their strength, so the number grows while the protection weakens.

The test of whether Hold is working: the last time the model was updated, did anyone re-run the guardrail tests before it went live? If not, the guardrails are only as good as whenever they were last proven.

There is no UAE or Dubai AI act. As of September 2026 no dedicated AI statute exists at federal or emirate level — AI is governed through the laws above. Claims of a binding “Dubai AI Act” with a 2027 deadline circulate online and do not survive checking against the law firm trackers. The federal counterpart is the UAE AI & Data Authority, approved 14 June 2026, which merged the AI Office, the TDRA's digital government arm and the UAE Data Office — and can propose legislation, which none of them could.

Eight rules to set by default

A starting list for any public-sector deployment, before anything sector-specific. Six of the eight can be enforced by architecture, because a government entity usually controls its own deployment end to end.

Must never happenEnforce it at
An adverse decision reaches a person without a human having reviewed itL4 — the system recommends, it cannot issue
One person's data appears in another person's sessionL4 — search scoped to the signed-in identity
Citizen data leaves approved residencyL4 — deployment topology, network route
Profiling for enforcement without a separate legal basisL4 — the data is not in the system
A person is not told they are talking to AIL4 — disclosure in the interface
A decision is taken that cannot be reconstructed laterL4 — logging as a hard dependency
Output states a legal or eligibility decision as finalL3 — output check on determinative language
Service quality differs across the languages servedL3 — tested and reported per language

Arabic is a guardrail problem, not a translation problem

Easy to miss, and an international vendor has no reason to raise it.

  • The software that checks AI output is trained mostly on English and is noticeably weaker in Arabic
  • Mixing both languages in one sentence is weaker still — and it is how people here write
  • Gulf dialect and Arabic typed in Latin letters are further outside the training data than Modern Standard Arabic
  • Report pass rates per language, never one blended number that hides the gap
Put this in the procurement questions. “Supports Arabic” means the model writes Arabic. It says nothing about whether the safety layer reads it. Different components, often different suppliers — and the second one is never in the demo.

Speaking the Charter's language

The UAE Charter's 12 principles are non-binding, which is why mapping to them is cheap and worth doing: a government counterpart sees their own framework reflected back.

TransparencyRule 5, plus dated evidence from Prove

AccountabilityA named owner per rule

The question to ask a government entity early: which of your guardrails would still hold if the AI decided to ignore them? The honest answer is the ones built into the architecture — and the useful follow-up is why the rest were not.
