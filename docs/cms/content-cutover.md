The legacy `VITE_CMS_CUTOVER_PEOPLE` switch is ignored, including when absent or false. There is no compiled people roster. Requested-market published suppression applies before approved CMS edition fallback; staged availability does not affect public delivery. People revalidate on mount, market changes, and window focus; pending revalidation does not render cached profiles. Deploy the updated website build once to remove the legacy path; subsequent CMS visibility publications require no code release.

Other `VITE_CMS_CUTOVER_*` switches are independent and default off. While a switch is off, an API/contract/empty state may use the compiled collection. Once on, empty stays intentionally empty and API or contract failure is observable instead of reverting to compiled content. Industry CMS revisions and the compiled fallback implement the same required contract; a partial industry payload is a contract failure, not permission to mix CMS and compiled fields.

## Industry contract baseline

The broadened industry baseline keeps content `schemaVersion: 1` and adds required `opportunity`, `capabilities`, and `selectedWork.description` fields. The schema-version discriminator remains the compatibility boundary; this additive editorial baseline does not change canonical slugs, routes, order, evidence classifications, governance fields, or market fallback.

Generated industry operations use the versioned `cms-industry-contract-v6:` receipt namespace. Replays are idempotent. A safe legacy edition must be published with its pointer on the latest revision and contain only the exact governed inventory revision followed by approved Pulse image-cutover revisions. Receipt/audit stored-result provenance, source-revision links when recorded, immutable stored content-digest presence, workflow states, and the historical payload relationship must all agree; reason text alone is insufficient. Older cutover audits that predate `sourceRevisionId` remain admissible only when their exact versioned receipt, revision order, and payload-copy relationship independently prove the chain. Payload comparisons use canonical object-key ordering so PostgreSQL JSONB ordering is not mistaken for editorial drift. Revision 1 is validated against its own stored inventory result, not today’s compiled payload. Each Pulse revision must be an exact copy of its prior stored payload except for governed `heroMediaId`/`mediaIds`, so a legacy `content.image` path remains immutable historical content. The current published revision must also carry one active/ready hero asset referenced by an exact immutable media-version pin. Reconciliation copies that asset and pin to a validated broadened snapshot, appends at the next revision number, and explicitly approves and publishes it. Every prior revision remains immutable.

V6 also recognizes the one known v3 defect narrowly: the exact provenance-backed broadened v3 revision matches today’s contract after only media identity is normalized, is published, has precisely one matching unpinned media reference, and immediately follows the exact governed Pulse revision with one active/ready immutable PNG pin. It appends a repaired immutable revision from the v3 snapshot, replacing only `heroMediaId`/`mediaIds` with that prior Pulse asset and pin, then validates and publishes it with explicit repair metadata. A correctly pinned v3 revision is reused without another revision. Any other missing-pin history, ambiguity, payload modification, provenance gap, reason/state/sequence difference, or pointer mismatch is preserved.

## Header navigation visibility

Administrators can independently enable or disable every registered header menu and submenu item from **Website Navigation** in the CMS. The registry owns labels and safe internal targets in code; the CMS owns only visibility. A disabled parent hides its complete submenu without deleting the saved child choices. Public delivery defaults to the complete safe registry if the settings API is unavailable, so an outage cannot strand visitors without navigation.
